# 任务：项目经理（orchestrator）角色 —— 门禁内置的会话编排层

> **⚠️ 这是 2026-08-29 那一轮的任务书，不是当前实现的说明。**
>
> 它被保留下来是因为「为什么要有项目经理这个角色」「用户的工作流长什么样」
> 「plan 为什么是编排层的 loop goal」这些**意图**至今成立，读它有价值。但
> 它描述的**机制**已在 2026-08-30 的通道重构里整体换掉：
>
> - 子会话 → 项目经理不再走 `lib/attention.ts` 的全局 attention 队列（已删除），
>   而是每个子会话一条**专属通道文件**；
> - 项目经理 → 子会话不再走 `tmux send-keys`（已删除），而是写通道 +
>   子会话侧门禁用 `pi.sendUserMessage` 注入；
> - 状态不再从 `capture-pane` 的屏幕文本推断，六态全部来自结构化真值；
> - `orchestrator_read` / `_key` 合并为 `orchestrator_answer`，`_status` 并入
>   `orchestrator_wait({timeoutMs:0})`，`_send` → `_instruct`，`_relay` →
>   `_handoff`，新增 `_recover` / `_attach`。
>
> **当前实现请读 `docs/orchestrator-supervision.md`**，那份文档逐节写明了
> 「被替换掉的是什么、为什么」。本文以下内容不再更新。


你在 pi-review-gate 仓库工作。本轮新增一个角色：**项目经理**，由门禁提供全套工具，负责
统筹、规划、调度子会话，把「一个 agent 一轮做不完的大需求」跑完。全程走 loop 门禁流程。

## 0. 总纲

**沿用**：重门禁、轻 Agent；default-on 无开关；沟通风格 = 高级助理（简洁、有信息量、
不说教）；用户介入统一走 `ask_user`；需求先澄清→反述→确认。

**本轮新增的一条（用户原话）**：**能提供工具的，就不要让会话自己组装。**
开子 agent、开新项目经理、发系统通知、与其他角色通信 —— 全部由门禁提供工具，项目经理
只负责「调用哪个工具」，不负责「怎么实现」。理由：现编的实现会出错。

> 实证：手工编排一轮（2026-08-29）暴露的全部问题都源于现编 —— 漏传
> `RG_PARENT_SESSION` 导致子会话的通知无人接收（只能靠用户口头转告）、等待方式反复出错、
> 派完任务就结束 turn 不再监听。这些在「调工具」的形态下都不会发生。

## 1. 角色定义与使用形态

**项目经理 = 纯编排层**：统筹、规划、调度、汇报。**不写代码、不解冲突、不做具体的事** ——
凡是耗上下文的活（改代码、解合并冲突、查历史）一律开子会话去做。

**用户的工作流**（必须支持）：

1. 用户自己开 tmux session，**每个项目/开发任务一个 window**
2. 在该 window 里启动一个 pi 会话，设为项目经理角色
3. 用户与项目经理约定任务（plan）
4. 约定完成后，**项目经理接手这个 window**，在其中开子会话推进
5. 用户随时可查看、可接管回来

**硬边界**：项目经理只能在**用户与它约定所在的那个 window** 内活动，不得影响其他 window，
**绝不能搞挂用户的 tmux session**。

## 2. 两个目标场景

1. **无人值守长任务**：晚上派发，用户去睡觉，早上验收。
2. **大需求分解**：一轮上下文做不完 → 先与用户约定分工 → 串行接力（一个任务完成再开下一个
   会话）或并行（约定并行数与任务边界，多 worktree，完成后合并）。

## 3. 工具集（门禁提供，项目经理只调用）

命名建议，可按仓库习惯调整：

| 工具 | 职责 |
|---|---|
| `orchestrator_plan` | 读写 plan（任务清单 + 状态 + 文件边界 + 依赖 + 串/并标记） |
| `orchestrator_spawn` | 在本 window 开交互式子会话 pane，**自动注入 orchestration id** |
| `orchestrator_send` | 向子会话发消息（含代批 goal 等交互） |
| `orchestrator_wait` | 等待子会话事件（判据见 §5） |
| `orchestrator_notify` | 给**用户本人**发系统通知（唯一入口 + 节流） |
| `orchestrator_relay` | 自我接力：开新项目经理会话并交接（见 §7） |
| `orchestrator_close` | 关闭一个子会话 pane（仅限自己登记的） |
| `orchestrator_status` | 一次读回全局状态（新接手的项目经理靠它续上） |

项目经理**不得**手写 tmux 命令、不得手写等待脚本、不得手写通知逻辑。

## 4. tmux 布局与安全约束（硬拦截）

### 4.1 布局（用户常用形态，实测于 window @1）

```
window (319x84)
├─ 左列 159x84   项目经理独占
└─ 右列 159x84   子会话纵向堆叠
   ├─ 子会话 1
   └─ 子会话 2
```

| 场景 | 命令 |
|---|---|
| 第一个子会话（右列不存在） | `split-window -h -t $TMUX_PANE` |
| 后续子会话 | `split-window -v -t <右列最后一个 pane>` |
| 自我接力 | `split-window -h -t <老项目经理 pane>`（新会话在其右，老 pane 关闭后自动扩展占据左列） |
| judge 角色（reviewer/goal-auditor/adviser） | 仍走 `pi -p` 后台进程，**不占 pane** |

pane 尺寸不管，用户自行调整。

### 4.2 全部 tmux 能力由门禁工具提供（用户要求）

**项目经理完全不碰 tmux 命令**。上表的每一种 split / send / kill 都封装在 §3 的工具里，
由门禁内部执行并记账（登记 pane id、归属、创建时间）。项目经理只表达意图
（"开一个子会话"、"关掉这个子会话"、"接力"），不表达手段。

理由（总纲那条哲学）：现编的 tmux 命令会错，而 tmux 出错的代价是**搞挂用户的工作环境**。

### 4.3 bash 层拦截 = 兜底，不是主路径

工具是唯一正路；bash 拦截只防"绕过工具自己敲命令"：

- `kill-session` / `kill-server` / `kill-window` —— 一律禁止
- `new-session` / `new-window` —— 禁止（只允许工具在本 window 内 split）
- `set -g` / `set-option -g` / `setw -g` —— 不得改用户全局配置
- 项目经理会话里手写的 `split-window` / `send-keys` / `kill-pane` —— 一并拦下，
  提示"用 `orchestrator_spawn` / `orchestrator_send` / `orchestrator_close`"

门禁工具内部执行 tmux 时不受此拦截（与现有 gate-owned 写入豁免同机制）。

## 5. gate mode 新增「项目经理」模式（用户要求）

复用现有 `set_gate_mode` 机制，在 `loop` / `explore` / `normal` 之外新增一个模式
（命名建议 `orchestrator`）：

| 模式 | 注入内容 | 工具 | 硬约束 |
|---|---|---|---|
| `orchestrator` | 编排职责、plan 协议、接力协议、决策权边界 | §3 全套编排工具 | §6 全部（禁写代码、plan 批准、全局 declare_done…） |
| `loop`（子会话） | 现有那套原样不动 | 现有工具原样 | 现有约束原样 |

**子会话侧只加一句话**（用户要求：不要给子会话注入编排内容）：让它知道"有一个项目经理在
管这轮任务，它可能会给你发消息"。plan、编排职责、调度细节**一律不注入** —— 子会话就是
普通的 loop agent。

模式判定：项目经理会话由用户手动 `set_gate_mode("orchestrator")` 进入；子会话由
`orchestrator_spawn` 启动时自动带 `loop` 模式，不会误入编排模式。


## 6. 通知与寻址

### 6.1 三条线，互不混淆

| 方向 | 机制 | 备注 |
|---|---|---|
| 子会话 → 项目经理 | attention（`lib/attention.ts` 已实现） | 定向，只有一个接收者 |
| 项目经理 → 子会话 | `orchestrator_send` | 封装 tmux send-keys |
| 项目经理 → **用户本人** | 系统通知（`pi-notify`，OSC 777） | **只有项目经理能调** + 节流 |

历史约束澄清：`lib/attention.ts` 里 "NO SYSTEM NOTIFICATIONS（user requirement）" 针对的是
**过去的广播**（任何会话发通知、所有会话都收到）。本轮的系统通知是**单一入口、只推给用户
本人、其他 pi 会话无感**，不违背该约束。

### 6.2 寻址必须用 orchestration id，不是 session id（关键）

`RG_PARENT_SESSION` 是进程启动时固定的环境变量，项目经理换会话后改不了 → 子会话仍往老
会话发，通知失联。

**解法**：channel key 改用稳定的 orchestration id（如 `orch-<repoHash>-<起始时间>`）：

- 注入子会话的是 `RG_ORCHESTRATION_ID`
- attention channel = `rg-attention-orch-<id>`
- 项目经理（新老都一样）监听同一 channel
- 自我接力时新会话接手**同一个 id** → **子会话完全无感，无需重启**

实现可直接复用现有 `RG_PARENT_SESSION` 字段、只改语义，代码改动最小。

### 6.3 `orchestrator_wait` 的判据

与 `judge_wait` **骨架相同、判据不同**（等待骨架的判据注入能力由上一轮任务交付）：

| | judge 子会话 | 编排子会话 |
|---|---|---|
| 形态 | `pi -p` 一次性 | 交互式长期存活 |
| "有事了" | 进程退出 | **attention 事件到达** |
| 正常终态 | 输出 verdict 后退出 | `declare_done` 后仍活着 |
| 异常终态 | exit-code 缺失 | 进程死亡 |

判据集：attention 事件 / 子会话 declare_done / 进程异常死亡 / 超时。

## 7. 门禁对项目经理的硬约束

**全部 14 条一次做完**（用户已定：不分批）。

1. **plan 必须经用户批准**才能开工 —— 编排层的 loop goal，未批准禁止 spawn 任何子会话
2. **项目经理禁止自己写代码** —— edit/write 一律拦，只放行 plan 文件与交接文档
3. **plan 中还有未完成任务 → `declare_done` 拒绝**（整体任务判断，不是单会话 goal）
4. **还有活着的子会话 → `declare_done` 拒绝**（类比现有 "judge child still open" 检查）
5. 每个任务必须声明文件边界
6. 边界重叠的任务禁止并行（自动降级串行）
7. 并行任务必须独立 worktree
8. 代批 goal 必须过边界比对（不符则通知用户）
9. 通知单一入口 + 节流（只有项目经理能调）
10. 工作分支未合并回基准 → 拒绝退出（除非明确记录「本次不合并」及理由）
11. 有挂起的用户决策项却未通知用户 → 拒绝退出
12. 接力时 plan 与交接文档必须已落盘，且**只能由新会话关闭老会话**
13. 子会话必须由 `orchestrator_spawn` 启动（手写 tmux 被拦，见 §4.3）
14. 「必须真人」的决策不得代答（见下方边界）


### 决策权边界（用户已定）

- **项目经理可自行决定**：技术取舍、`/gate-bypass`、代批 goal（需与 plan 边界一致）
  —— 全部**留档 + 汇报**
- **必须叫用户**：丢弃工作区（不可逆）、敏感文件授权

## 8. 自我接力协议

```
1. 老会话检测上下文接近阈值（如 85%）
2. 老会话：写交接文档 + 更新 plan + 进入 idle（不再动手）
3. 老会话：split-window -h -t <自己> → 启动新项目经理，传三样：
     · orchestration id（继承通知渠道）
     · 交接文档 + plan 路径
     · 老会话 transcript 路径（~/.pi/agent/sessions/<encoded-cwd>/<ts>_<id>.jsonl）
4. 新会话：读交接文档 + plan；有疑点时按需 grep 老 transcript
     （已有先例：prepare_adviser 就是给 transcript 指针让它自己去捞）
5. 新会话：确认无误 → kill-pane 老会话 → 自动扩展占据左列
6. 子会话通知因寻址 orchestration id，自动流向新会话
```

**关闭老会话只能由新会话执行** —— 这天然证明新会话已经起来并接手成功，中间不断档。

交接文档是老会话的**自述**（可能遗漏或美化），transcript 是**原始记录** —— plan 执行出问题
时，新会话能回到原始记录里找线索。

## 9. 开发规范：两阶段掐死（用户要求）

不只是长文件，**架构 / 抽象 / 模块化 / 语义化 / 模块与文件的分工全局意识**都要管。

| 阶段 | 角色 | 做法 |
|---|---|---|
| **前置** | `goal-auditor` | 目标阶段就否掉会造成架构劣化的方案（如「继续往 8296 行的文件里堆」）—— 这道关最值钱，比写完再重构便宜得多 |
| **后置** | `reviewer` | 架构/抽象/模块化/语义化写进**代码改动审查主清单**，作为可出 P1 的正式条款 |

现状问题：`agents/reviewer.md` 里只有 "Alignment with existing architecture"、"Architecture
drift or tech debt" 两句泛泛表述，且位于「审查计划 / 审查整体代码库」段落，**不在审查代码
改动的主路径上**。

**机械部分**（只有一层是硬的）：

| 层 | 做法 | 硬/软 |
|---|---|---|
| 新建文件超阈值（如 600 行） | 硬拦 | 硬 |
| 存量文件超阈值 | 只提醒（"此文件已 N 行，本次 +M，考虑拆分"） | 软 |
| goal 阶段碰热点文件 | 注入「先评估是否该拆」 | 软 |

**为什么不对存量硬拦**：8296 行不是一次写出来的，是几十次「只加 100 行」累积的，每次单看都
不值得拦；写完再拦已经太晚，只会逼 agent 在收尾时硬拆，拆得更烂。

**本仓自己就是最严重的反例**（`extensions/review-gate.ts` 8296 行，含 27 个 registerTool +
L1/L6/L7/L8 全部关卡 + 持久化 + 输出通道）。加硬拦截前必须先解决这个悖论，否则规则形同虚设。
