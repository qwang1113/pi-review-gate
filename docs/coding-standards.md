# 代码规范 — 开发与审核的共同准绳

开发和审核阶段必须共同遵守的质量底线。主会话按它写，审核者按它审。
目标是**又快又好地收敛**：优先主流程与常规旁路分支，不在特别小众的
边界上死磕（可列为 Note，不升级为阻塞）；但**安全相关、对外暴露相关**
的边界必须覆盖。本项目为单用户本地优先项目，这一优先级成立。

## 1. 架构原则

- **深模块**（A Philosophy of Software Design）：接口小、功能强；复杂度
  藏在实现里，不泄漏给调用方。追求"把错误定义掉"——设计上让错误不可
  表达（类型系统、状态机），优于事后到处检查。
- **KISS / DRY / YAGNI**：先写最简单的正确版本；重复第二次才抽象；不写
  "以后可能用得上"的东西。
- **SOLID**：单一职责（一个模块只有一个理由去变）；依赖倒置（面向抽象
  与接口，不面向具体实现）。
- **Unix 哲学**：一个程序只做好一件事，靠组合而非大一统。
- **显式优于隐式**（Zen of Python）：显式传参、显式错误处理，不用魔法；
  扁平优于嵌套；可读性优先。
- **无过早优化**（Knuth）：先清晰正确；性能靠 profiler 数据说话，不靠
  猜。加复杂度必须有测量支撑。

## 2. 编码实操

- 卫语句提前返回，消灭箭头型嵌套。
- 函数只做一件事；参数超过 3 个打包成对象。
- 命名自解释：好的命名删掉大多数注释；注释写"为什么"，不写"是什么"。
- 优先不可变数据和纯函数——状态少，bug 少。
- 不写"聪明"代码（Kernighan：调试比写代码难一倍）。
- 童子军规则：每次改动让代码比来时更干净一点。
- **收敛原则**：聚焦主流程与旁路分支；小众边界列 Note，不死磕；安全与
  对外边界必须考虑。

## 3. 本项目的落地规则（TypeScript / Node）

- 格式听工具：Prettier / ESLint 按项目配置执行，人工不争论格式。
- 类型系统表达约束：少用 `any` / `as`；运行时校验与 typebox schema
  保持一致。
- 测试必须含行为断言；断言缺失、仅为覆盖率服务的测试是 **P1**。
- 行为 / API / 配置变更必须同步项目文档（`README.md`、`docs/`、spec 类
  文件，本仓库的 `AGENTS.md` 同时是架构规范，按目标要求更新时计入）；
  只触碰 agent 记忆文件（CLAUDE.md）不算文档更新。

## 4. 审核时的应用

- **审核分两轮，但不是串行（2026-09-16 起）**：`quality-auditor` 的**代码质量轮**
  与 `reviewer` 的**功能轮**审同一段 commit range，由同一次 `judge_submit`
  **同时启动**，谁先判不过由取消矩阵收口（正文与矩阵只有一处：
  `docs/execution-model.md` §「并行三方与取消矩阵」）。质量轮审的就是本节与
  §1/§2/§5 这些原则（审查问题清单见 `docs/code-quality-rules.md`，一份不复制此处
  的条文）；功能轮审需求符合度 / 测试覆盖 / 文档同步。本文是**开发准绳**，
  质量轮是它的**审查面**——两者引用同一份条文，不各写一遍。
- 按上述原则审，优先级：架构合理性（职责 / 复杂度 / 错误面）> 正确性
  （主流程 + 旁路）> 命名与可读性 > 风格。
- 严重度：**P0** 破坏性 / 安全 / 数据问题；**P1** 应修（含断言缺失、
  文档脱节、一类边界漏列）；**P2** 值得修；**Nit** 风格。
- 一类问题（同一函数的不同输入、同一问题的变种）**一轮列全**，不挤牙膏、
  不来回拉扯。

## 5. 最小化准则（Minimalism）

本节是最小化准则的唯一实质出处，其他面只引用不复制。

- **YAGNI，不存在必要就不写**：推测性需求直接跳过，并用一句话说明跳过了什么。如：不要为「以后可能要配」加 config 开关，能默认安全就默认安全。
- **复用优先，先找后写**：本仓库已有 helper / util / 类型 / 模式、标准库、平台原生能力、已装依赖能覆盖的，一律复用。如：不要为单个用例新增依赖，几行代码能解决的不引入新包。
- **能删就删，先删后加**：可删的代码、可合的行、可替的抽象先处理，再写新代码。如：修 bug 先找根因，在共享函数加一处 guard，优于在每个调用方叠补丁。
- **新依赖须论证**：每新增一个依赖都要有书面论证，说明现有代码 / 已装依赖为什么做不到。如：论证随改动走，写进送审说明或提交说明正文。

严重度映射：写代码时只是习惯提醒，不阻塞；审目标 / 审计划时，范围外工作与过度设计可出 P1；审代码 diff 时，可删代码、新增依赖无论证、重复实现可出 P1，其余最小化意见为 P2。

## 6. 写作时规范（写之前看这一节）

这一节的存在理由是**规范前置**：写的时候就做对，而不是等 quality-auditor 打回。
它与 §1 / §2 / §5 是同一份准绳的不同截面，不重复它们的条文。

- **安全**（写作时的第一顺位，不靠审核兜底）：外部输入 —— 用户输入、文件内容、
  命令输出、网络响应 —— 进入 shell 命令、文件路径、SQL、正则之前，先转义或走
  白名单；拼接即漏洞。权限与越权边界显式检查，不靠调用方自觉。敏感信息
  （token、密钥、凭据、个人数据）不落盘、不进日志、不进提交信息。破坏性操作
  （删除、覆盖、`git push --force`、`reset --hard`、批量改写）要显式确认。
- **模块落点与规模**：新增一项职责之前先问「它落在哪个模块」，答案要能一句话
  说出来；答不上来是还没想清楚，而不是「先写在手上这个文件里」。别往已经很大的
  文件里加 —— 存量大小只提醒不硬拦，但它是落点判断的输入；新建源文件超过 600 行
  在 checkpoint 被硬拦（`lib/file-size-gate.ts`）。
- **注释**：写「为什么」（约束、反直觉的取舍、踩过的坑），不写「是什么」——
  §2 已有一条，这里补的是判据：把这条注释删掉，代码更难读 ⇒ 它在解释为什么，
  留下；删掉后只是少了一句复述 ⇒ 它是噪音，删掉，让命名承担（§2「命名自解释」）。
- **嵌套与提前返回**：嵌套超过 **3 层**就用卫语句消掉。§2 第一条给了写法，
  这里给阈值 —— 3 层是可读性的上限，不是风格偏好。
- **依赖与开源**：外面有成熟实现时，先看它是否**真的贴合本项目** —— 接口、规模、
  维护面、它带进来的复杂度都要对得上，而不是「有人做过」就足够。用不用**从需求
  本身出发**决定。这一条是**判断提示**，不是硬要求：不要求每次都去搜开源，也
  不要求自研就写论证（书面论证只针对新引入的依赖，见 §5）。

## 7. 面向 agent 的失败文案（门禁对 agent 说的「不行」）

门禁拒绝 agent 的每一句话都必须是**可执行的**，而不是一句判词。三件套缺一不可：

- **现象**：什么被拒了 —— 具体到这个调用、这个文件、这一条。
- **原因**：门禁凭什么拒。是**事实**（哪个常量、哪次测量、哪条记录），不是措辞
  ——「不符合规范」不是原因。
- **下一步**：agent 自己就能做的动作；**不能自修时写明谁能解**（用户 / 门禁 / 
  第三方），并说清那个人需要什么信息才能解。

形状由 `lib/rejection-copy.ts` 唯一实现：调用方填「现象 / 原因 / 下一步 + 谁能解」
四个字段，渲染只有那一处，漏字段编译不过。新增拒绝点一律用它，存量随改动收敛。
**其他面只引用本节，不复述三件套。**
