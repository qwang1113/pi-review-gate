# 代码规范 — 开发与审核的共同准绳

开发和审核阶段必须共同遵守的质量底线。主会话按它写，审核者按它审。
目标是**又快又好地收敛**：优先主流程与常规旁路分支，不在特别小众的
边界上死磕（可列为 Note，不升级为阻塞）；但**安全相关、对外暴露相关**
的边界必须覆盖。本项目为单用户本地优先项目，这一优先级成立。

## 1. 架构原则

- **深模块**（A Philosophy of Software Design）：接口小、功能强；复杂度
  藏在实现里，不泄漏给调用方。追求"把错误定义掉"——设计上让错误不可
  表达（类型系统、状态机），优于事后到处检查。
- **KISS / DRY / YAGNI**：先写最简单的正确版本；重复第二次才抽象；不写
  "以后可能用得上"的东西。
- **SOLID**：单一职责（一个模块只有一个理由去变）；依赖倒置（面向抽象
  与接口，不面向具体实现）。
- **Unix 哲学**：一个程序只做好一件事，靠组合而非大一统。
- **显式优于隐式**（Zen of Python）：显式传参、显式错误处理，不用魔法；
  扁平优于嵌套；可读性优先。
- **无过早优化**（Knuth）：先清晰正确；性能靠 profiler 数据说话，不靠
  猜。加复杂度必须有测量支撑。

## 2. 编码实操

- 卫语句提前返回，消灭箭头型嵌套。
- 函数只做一件事；参数超过 3 个打包成对象。
- 命名自解释：好的命名删掉大多数注释；注释写"为什么"，不写"是什么"。
- 优先不可变数据和纯函数——状态少，bug 少。
- 不写"聪明"代码（Kernighan：调试比写代码难一倍）。
- 童子军规则：每次改动让代码比来时更干净一点。
- **收敛原则**：聚焦主流程与旁路分支；小众边界列 Note，不死磕；安全与
  对外边界必须考虑。

## 3. 本项目的落地规则（TypeScript / Node）

- 格式听工具：Prettier / ESLint 按项目配置执行，人工不争论格式。
- 类型系统表达约束：少用 `any` / `as`；运行时校验与 typebox schema
  保持一致。
- 测试必须含行为断言；断言缺失、仅为覆盖率服务的测试是 **P1**。
- 行为 / API / 配置变更必须同步项目文档（`README.md`、`docs/`、spec 类
  文件，本仓库的 `AGENTS.md` 同时是架构规范，按目标要求更新时计入）；
  只触碰 agent 记忆文件（CLAUDE.md）不算文档更新。

## 4. 审核时的应用

- 按上述原则审，优先级：架构合理性（职责 / 复杂度 / 错误面）> 正确性
  （主流程 + 旁路）> 命名与可读性 > 风格。
- 严重度：**P0** 破坏性 / 安全 / 数据问题；**P1** 应修（含断言缺失、
  文档脱节、一类边界漏列）；**P2** 值得修；**Nit** 风格。
- 一类问题（同一函数的不同输入、同一问题的变种）**一轮列全**，不挤牙膏、
  不来回拉扯。
