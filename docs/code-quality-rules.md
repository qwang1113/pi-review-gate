# 代码质量判定表 —— quality-auditor 的唯一实质出处

质量轮（`agents/quality-auditor.md`）读的就是这张表。它是**审查问题清单**：
每条是一句审查员必须回答的问题，答「否」就是一条 finding。

背后的一般原则（深模块、KISS/DRY/YAGNI、卫语句、不可变、童子军规则、最小化四条……）
的唯一实质出处仍是 `docs/coding-standards.md`（§1 架构原则、§2 编码实操、§5 最小化准则）。
本表**只写审查时该问什么、什么级别阻塞、哪些不归你**，不复制那些条文——两份副本
迟早会分叉，而分叉的那一份会被当成规则用。

## 判定对象与对照物

- **判定对象**：本轮改动的行（不可变 commit range `baseline..HEAD`）。存量代码本身不判。
- **对照物**：**整个仓库**。改动是否成立，取决于仓库里已经有什么——见「跨库对照」。
- 语言无关：这套问题对 TypeScript / Rust / Shell / Python / 前端都一样成立。

## L1 · 哲学 / 架构 / 正确性 / 安全 / 性能（P0/P1 —— 阻塞）

### A 正确性

| # | 问题 | 级别 |
| --- | --- | --- |
| L1-A1 | 有没有**明确的逻辑 bug**：条件写反、边界差一、状态机漏态、并发竞态、资源不释放、错误被吞掉后继续跑？ | P0 |
| L1-A2 | 有没有**语言层面的坑**直接导致错误结果：浮点相等比较、可变默认参数、闭包捕获循环变量、整数溢出、未 await 的 promise、shell 未加引号的变量展开……？ | P0 |
| L1-A3 | 错误**尽早暴露**了吗：不合法输入在入口被拒绝；能用类型 / 约束 / 状态机把错误定义掉的，还在靠运行时到处检查？ | P1 |

### B 少即是多

原则见 `docs/coding-standards.md` §5（那是唯一实质出处，不在此复述）。审查时问：

| # | 问题 | 级别 |
| --- | --- | --- |
| L1-B1 | 这段代码**需要存在吗**？解决的是用户要的问题，还是「以后可能用到」的推测性特性、开关、参数、抽象、兼容层？ | P1 |
| L1-B2 | **仓库里已经有能覆盖它的东西吗**（本仓 helper / 类型 / 模式、标准库、框架自带、已装依赖）？新依赖有一句话说明为什么现有手段做不到吗？ | P1 |
| L1-B3 | **两套实现并存**吗——新路径落地时旧路径删了没有，有没有 `legacy` / `v2` / `advanced` 这类后门？ | P1 |
| L1-B4 | **同一事实只有一个出处**吗？常量 / 规则 / 校验逻辑有没有出现在两处；门禁或框架已经强制的规则，业务里是不是又手写了一遍？ | P1 |
| L1-B5 | **能删的删了吗**——本次改动带来的死代码、无人调用的导出、注释掉的代码、不再需要的分支？ | P1 |

### C 架构：做好一件事

| # | 问题 | 级别 |
| --- | --- | --- |
| L1-C1 | 新代码落在**职责能用一句话说清**的模块里，还是落在「刚好打开的那个文件」里？说不出这个模块的职责，就是还没想清楚——改动往**已经很大的文件**里加职责的情形，判据见 L1-C8。 | P1 |
| L1-C2 | 每个函数 / 方法 / 类**只做一件事、只在一个抽象层级**吗？名字里有 And / Or，或一段里既有底层细节（拼字符串、遍历、IO）又有业务决策，就是没做到。 | P1 |
| L1-C3 | **是面条代码吗**——重复出现的结构（相似的 if-else 链、复制粘贴改一处的两段、每个 handler 都写一遍的前置检查）能否抽成公共函数 / 类 / 中间件 / 装饰器 / 切面？框架给了横切机制的（midway 的装饰器、切面、IoC），日志 / 鉴权 / 校验 / 事务 / 缓存 / 重试就该走它，不该在每个方法体里手写。 | P1 |
| L1-C4 | **该用设计模式的地方用了没有**（按类型 / 状态分派行为的 switch / instanceof 链 → 多态 / 策略 / 状态；层层可选行为 → 装饰器 / 管道；构造分散且参数一堆 → 工厂 / 建造者）；反过来，**不该硬套的套了没有**（只有一个实现的接口、只有一个产品的工厂、三行逻辑的策略类）。 | P1 |
| L1-C5 | **依赖方向对吗**——高层依赖的是抽象还是具体实现（类里直接 `new` 具体服务、模块直接读全局配置），导致它测不了、换不掉？ | P1 |
| L1-C6 | **接口小、实现深吗**——新暴露的 API 有没有让调用方知道不该知道的细节（要传五个来自内部状态的参数、要按顺序调三个方法）？ | P1 |
| L1-C7 | **副作用显式吗**——函数改了入参 / 全局 / 外部状态而名字和位置没说；本该不可变的数据被就地改了？ | P1 |
| L1-C8 | **它是不是给一个已经很大的文件又加了一个职责**——落点在动手前说得出来吗？`lib/file-size-gate.ts` 只硬拦**新建**文件超过 600 行，存量文件的继续膨胀没有任何机械拦截，所以这一条就是那半的替代：改动往一个已多职责 / 已很长的文件里加新职责时，必须答得出「新代码该落在哪个模块」，答不出就是还没想清楚（判据见 `docs/coding-standards.md` §6「模块落点与规模」）。 | P1 |

### D 性能（只看明显的，不做过早优化）

| # | 问题 | 级别 |
| --- | --- | --- |
| L1-D1 | 有没有**明显的性能事故**：循环里做 IO / 查库（N+1）、O(n²) 处理本可线性的集合、热路径反复计算同一结果、无界内存增长、串行等待彼此无关的异步？ | P1 |
| L1-D2 | 反过来，有没有**为没测过的性能问题**写复杂代码：手写缓存、对象池、牺牲可读性的微优化，却没有数据？ | P1 |

### E 安全（P0/P1 —— 必答，不适用「小众边界可放过」）

安全的**写作时**版本在 `docs/coding-standards.md` §6（实质条文只在那里，不在此复述）；
这里是审查端：把它变成必须逐条回答的问题。安全边界不属于「收敛范围」里可以放过的
小众边界——**一条都不许因为「单用户、本地优先」跳过**。

| # | 问题 | 级别 |
| --- | --- | --- |
| L1-E1 | **注入**：外部输入（用户输入、文件内容、命令输出、网络响应）有没有未经转义 / 白名单就进入 shell 命令、文件路径、SQL、正则？拼接出来的命令 / 路径 / 语句，能不能被输入改写语义（多一个空格就变成另一个参数、`..` 越出目录、正则元字符改变匹配）？ | P0 |
| L1-E2 | **权限与越权边界**：新增的读 / 写 / 执行 / 网络出口越出它该有的范围了吗——读了不该读的路径、写到仓库之外、把门禁自己的状态文件当成可写输入、把「调用方已经检查过」当成这一层的许可？ | P0 |
| L1-E3 | **敏感信息**：token / 密钥 / 凭据 / 个人数据有没有落盘、进日志、进提交信息、进错误文案或测试 fixture？写出去之前问过「这份文件本来就该被提交 / 被打印吗」吗？ | P0 |
| L1-E4 | **破坏性操作**：删除、覆盖、`git push --force`、`reset --hard`、批量改写有没有先确认目标与范围（路径来自变量时先断言它在允许的目录内），失败路径能不能保住用户的数据？不可逆的数据丢失路径按 P0。 | P1 |

## L2 · 简洁 / 可读 / 可维护（明显的 P1，轻微的 P2）

| # | 问题 | 级别 |
| --- | --- | --- |
| L2-1 | **语义明确吗**：名字能读出它是什么 / 做什么；同一概念全仓库一个词；谓词用肯定式；魔数 / 魔字符串有名字。 | 看不出含义 = P1；可以更好 = P2 |
| L2-2 | **嵌套过深吗**：超过 3 层 if / 循环 / 回调；能用卫语句提前返回、拆函数或查表消掉。 | P1 |
| L2-3 | **函数尺寸**：一屏放不下且能切出命名子步骤；参数超过 3 个还没打包成对象。 | P1 |
| L2-4 | **有没有写聪明代码**：一行做三件事、依赖求值顺序 / 隐式转换 / 位运算代替布尔——读者得停下来解码的地方。 | P1 |
| L2-5 | **注释说的是为什么吗**：解释「是什么」的注释、日志式注释、横幅、注释掉的代码是 P2；关键的非显然决策（为什么绕开、为什么顺序不能动）**没有**注释是 P1。 | P1 / P2 |
| L2-6 | **童子军**：本次改动触及的函数里显而易见的旧问题，顺手清了吗（范围见下）。 | P2 |
| L2-7 | **一致性**：和周围代码的风格、错误处理方式、命名约定一致吗，还是同一个文件里两种做法？ | P2 |
| L2-8 | **可测试性**：新逻辑能否不启动整个宿主就测到；纯逻辑是不是被埋进了入口 / 框架回调里？ | P1 |
| L2-9 | **测试本身的质量**（有没有测是 reviewer 的事）：一个用例一个概念、名字说明期望、无共享可变状态、有断言。 | 无断言 = P1；其余 P2 |

## 跨库对照（L1-B2 / L1-C3 / L1-C4 / L2-6 怎么落地）

判定对象是本轮改动，**依据是整个仓库**——这三件事必须去读既有代码才答得出来：

1. **重复实现**：本轮新增的每个函数 / 方法 / 类型，在仓库里搜一遍同名与同类——
   别处已有等价实现（名字不同也算）⇒ L1-B2，要求删掉新增的那份、复用既有的。
2. **共同的抽象 / 设计模式**：本轮的抽象与既有模块是否其实是同一件事（两套节流、
   两套重试、两个 handler 各写一遍的同一状态机）⇒ L1-C4，指出可统一的形态，
   说清统一后谁适配谁。
3. **顺带清理**：本轮必须改的那个函数 / 文件本身已经很乱（长、嵌套深、命名糊）
   ⇒ L2-6，指出清理内容与代价，**不自行扩大范围**。

这三类结论若**只靠改本轮改动就能落地**，按上表出正常 finding；若**必须改既有代码**
（替换别处的实现、统一两处抽象、清理不属于本轮的旧代码），走下面一节。

## 涉及既有代码的提议：问用户，不问自己

范围归用户。发现「要动既有代码才能修好」时：

- 调 **`ask_user`** 提一个 2–4 选项的问题（每题带 A/B/C 字母编号，门禁会补上推荐项标记与「✎ 不选，我说明原因」行），
  典型选项：① 纳入本轮，一并处理 ② 本轮只改自己新增的那部分 ③ 记为范围外 / 技术债。
- 把结论写进对应 finding 的 `issue`（`[范围外提议] …` 开头，注明用户的选择）。
- **不要自己把范围扩大**：既不能因为「顺手」就把既有模块重构了，也不能把这类提议
  当成阻塞项——用户选了③它就只是记录。
- 这类提议不阻塞本轮：severity 用 P2（除非用户选了①，那时它随本轮改动一起被审）。

## 不审的（明确排除，别在这里出 finding）

- **语言 / 框架层最佳实践**：`any` vs `unknown`、lint 规则、惯用写法、格式化——
  各仓库自己的 lint / clippy / shellcheck / prettier 管这个，重复一遍只是噪音。
  （特例：某个写法在**这个仓库**里会直接产生错误结果，那是 L1-A2 正确性，照出 P0/P1。）
- **格式**：引号、分号、缩进、换行、导入顺序。
- **需求符合度、验收标准、测试覆盖率、文档同步、loop goal**——那是 reviewer 的判定，
  不在这里重复（重复只会给同一次改动记两笔账）。
- **既有代码本身**（本轮没改的行）：不判，除非它属于上面「跨库对照 / 顺带清理」。

## 输出要求

- 每条 finding：`层级-编号 · file:line · 一句话问题 · 一句话改法`。给不出改法的降 P2。
- 一类问题一轮列全（同一函数的所有分支、同一模式的所有出现），不挤牙膏。
- 先 L1 后 L2；L1 已有 P0/P1 时 L2 可以不写全。
- 只有 P0/P1 阻塞本轮；P2 只记录。
