# 改门禁与写测试

三条都指向同一件事：**门禁自己也是它自己的调用者**。改动看起来只影响 agent 那一侧，实际同时改掉了门禁内部那条没人盯着的链路。

## 1. 改共享实现的返回语义前，先枚举全部调用者

一个返回值被两类调用者消费时，「让 A 更好用」的改动往往同时**改坏了 B**——而 B 是门禁自己内部的链路，没有人会替它报错。

### 枚举法（三处都要查）

```
grep -rn 'callTool("<工具名>"' extensions/ lib/     # 1. 显式调用点
grep -rn '<registerXxx>' extensions/ lib/           # 2. internalHost 注册点
grep -rn '<工具名>' lib/*directives*.ts lib/*prompt*.ts  # 3. 注入文本里提到它的地方
```

枚举完不是就完了：**按调用者类别各验收一遍**。agent 侧走通了不代表门禁内部那条走得通。

### 实证 A（2026-09-05，修复 `c074b86`）

`judge_wait` 改成消息驱动后，打断了**门禁自己的 goal/plan 审计链**：审计链调一次 `judge_wait` 并把「不是 report」当成审计没跑完，而每个审计员在下结论前都会先流式吐 finding——于是第一条 finding 就把审计员中途关掉了，**任何带 findings 的草稿永远 fail closed**。修复 `c074b86`（`awaitRoundReport`：在消息驱动之上重调同一个工具直到本轮真正结束）。

### 实证 B（2026-09-05 稍后，同一根因再次命中，修复 `92056f7`）

把审计回合收敛成一个引擎（`dc6d886`）后，`judge_wait` 与同步审计链**共用了结论段**：wait 推进消费游标，同步链随后必然撞 `already-consumed`，于是**每一次 goal/plan 审计都 fail-closed**。修复 `92056f7`——它改用「一次记录必然留下的那对写入」（pending 被消费 **且** 游标前移）来判定「本轮已被 wait 收掉」。

这条值得点名的地方有三个：

1. **同一个根因连续两轮命中。** `c074b86` 修的是「wait 的语义变了，门禁自己的链没跟上」，`92056f7` 修的是「wait 和门禁自己的链共用了状态」——形状完全一样。
2. **它躲过了类型检查、全量测试和三遍通读**，最后是一次独立 `adviser` 咨询抓到的。
3. **结构性不可观测**：做这件事的会话跑的是**启动时加载的旧扩展**，它改的新代码根本不在自己的运行时里，所以「我跑一下试试」这条路在这里是不通的。

`92056f7` 的提交正文还点出了另一半根因，直接关系到第 2 条：

> The test fake now deletes the pending entry in forgetPending, matching the extension's dropAudits. **The unfaithful fake was what let the defect through.**

fake 与真实实现的行为不一致时，测试绿得毫无意义。改共享实现时，**同步检查每个 fake 是否还忠实**。

### 做法

改共享返回语义时，按顺序做完这四步：

1. 枚举三类调用点（上面的三条 grep）；
2. 给**每一类**调用者各写/各跑一条验收，不要只验 agent 那一侧；
3. 检查所有相关 fake 是否仍与真实实现同构；
4. 自己跑的运行时是旧扩展时，明说这一点，并用 `adviser` 咨询补上你看不见的那一半。

## 2. 循环类被测对象：加调用次数 trip wire

测一个「必须留最小间隔」的循环时，常用假时钟，而**假时钟只在 `sleep` 里推进**——这正是重点，暂停本身就是进展。但它带来一个后果：把间隔删掉的变异体**永远到不了 deadline**，于是测试**挂死**而不是失败。

### 实证

一次 reviewer 的变异运行因此**占满 CPU 22 分 43 秒**，最后靠人工 `pkill` 结束。修复 `b0875b3` 之后，同一个变异体在毫秒级失败并说明原因。

现在的写法在 `test/judge-lifecycle.test.ts:223`：

```ts
if (calls > 100) throw new Error("awaitRoundReport spun: the minimum gap is gone");
```

### 通则

被测对象里有循环、轮询、重试、退避时，除了断言「行为对」，再加一条**调用次数上限**。它不改变正确实现的任何行为，却把「挂死」变成「一句话说清的失败」——挂死会吃掉一次审查的全部预算，而且没人知道它在等什么。

## 3. 从源码窗口推导事实的结构测试：先自证推导，再断言结论

「扫源码得出一份清单，再拿清单下结论」这类测试有个隐蔽的失败模式：**推导漏掉一半输入时，结论恒为真，测试永远是绿的**。

### 实证

`agentVisibleTools()`（`test/extension-structure.test.ts:2443`，随 `c074b86` 引入）初版漏掉了一批真实注册的工具（当时的复盘记为 7 个；该计数未经逐一复核，但下列三处补偿本身可以直接读到），三个原因在最终实现里各留下一处补偿：

- **多行参数截断了窗口** → 正则放宽成 `pi\.registerTool\(\{\s*\n?\s*name: "([a-z_]+)"`；
- **链式注册**（一个 registrar 里再调下一个）→ 用 `queue` 做广度遍历；
- **`name` 是常量而非字面量**（`name: JUDGE_CONCLUDE_TOOL`）→ 回到声明它的模块里解析常量。

漏掉这些的版本，"没有任何注入文本提到不存在的工具" 这个结论照样成立——因为它压根没看见那些工具。

### 自证长这样

断言结论**之前**，先断言推导本身可用：它必须看见几个已知存在的项，且必须**看不见**一个已知的内部项（`test/extension-structure.test.ts:2489-2492`）：

```ts
const surface = agentVisibleTools();
assert.ok(surface.has("judge_submit") && surface.has("judge_wait") && surface.has("ask_user"),
  "the derivation itself must work before its verdict means anything");
assert.ok(!surface.has("judge_close"), "…and it must NOT see what only internalHost got");
```

正例证明它没漏，反例证明它没滥收。两条都要有——只有正例时，一个「把所有名字都收进来」的坏推导也能通过。

### 延伸：结构测试钉的是「形状」，重构时会成批失效

结构测试断言的是源码长什么样，不是行为是什么。所以一次正常的重构（把模块拆开、把措辞抽出去）会让它们**成批变红**，而这些红**不代表缺陷**。把审计回合收敛成引擎的 `dc6d886`、以及紧接着把措辞拆出去的 `e66e111`，就各踩到一次。

接受这个代价的前提是它在保护一件行为测试够不到的事（比如「注入文本不能提到不存在的工具」）。所以：

- 写的时候就把**这条测试保护的是什么**写进断言消息或注释，让下一个人能判断该修测试还是该修代码；
- 重构导致成批变红时，**逐条判断**是形状变了还是保护没了，不要整批放宽。
